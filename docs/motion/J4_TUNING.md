0.32 Nm harder than the joint's friction.** The runner feeds 0.5 Nm × tanh(v_ref/0.02) forward on J4; the logs say
J4's moving friction is **0.19 ± 0.05 Nm** (7 runs; 0.172 ± 0.011 without the low-speed box). Regression of

This reproduces the plan's §2 table to the digit (it lists the first six runs).

1. **Implied Coulomb 0.15-0.18 Nm on every run that reverses J4 at speed**, the same number the gravity fit found
   independently (0.15 Nm, GRAVITY_MODEL §5.2). Up and down agree within ±0.06 Nm with no consistent sign (the hearts
   0.21/0.15, the showreel 0.17/0.16, the figure-8s 0.23/0.12 and 0.13/0.25), so one symmetric value fits. The box is
   the outlier because at |v| ≤ 0.07 rad/s the sign and viscous columns cannot be separated (viscous −2.2, R² 0.78,
   and the fit moves a lot with the derivative filter, `analysis` README).
2. **No inertia, no usable viscous term** at these speeds (|v_ref| ≤ 0.18 rad/s; inertia < 0.01 Nm; the viscous
   coefficients scatter around zero, −0.56..+0.45). Nothing to feed forward beyond Coulomb and gravity.
3. **What 0.18 Nm would have done** (quasi-static what-if, each sample moved by (0.5 − 0.18)/40 × tanh): trajectory
   rms 7.4-7.7 → 2.0-2.4 mrad, sign term → −0.5..+0.4 mrad. The approach from the fold improves too (5.4-7.6 → 3.6-5.9
   mrad); **the return gets slightly worse** (3.0-4.8 → 3.4-5.6 mrad): its small error is a gravity error that the
   friction over-compensation happens to cancel (the gravity model, not friction, is the fix there). Approach and
   return move J4 in one direction while the gravity error changes with the pose, so their own sign terms are not a
   friction measurement (implied −0.16..+0.10 Nm approaching, 0.36-0.54 returning).
4. **The 3 Hz ripple is partly shared with J3**: coherence 0.47-0.62 at 2.5-3.3 Hz on the hearts and the box (above the
   0.35-0.39 zero level), 0.12 on the showreel. Of J4's 2.5-40 Hz band rms (1.1-1.7 mrad; the box 0.7), the part
   linearly shared with J3 is 0.6-1.4 mrad and J4's own 0.9-1.05 mrad. Note that "shared" is not "out of J4's reach": J4's own kd raises
   its dynamic stiffness at the ripple line, |kp + i·2π·3.3·kd| = 45 → 74 Nm/rad from kd 1 to kd 3 (§5).
5. **J5 is over-compensated the same way** (side finding): implied 0.116 ± 0.013 Nm against 0.3 fed forward, sign term
   −4.5 mrad, R² 0.86-0.89. Not part of this A/B; `--friction j5=0.12` is the same flag.
6. J1 (0.99 ± 0.07 vs 1.0 fed forward), J2 (1.16 ± 0.15 vs 1.0) and J3 (1.99 ± 0.14 vs 2.0) are right; their errors
   are not friction-dominated (R² 0.01-0.33).

Order of expected gain on J4, unchanged from the plan: (a) Coulomb 0.5 → 0.18 Nm (the dominant term), (b) the gravity
model (the constant −3..−8 mrad), (c) kd 3 for the ripple, (d) kp 50 (the guard cap; ×0.8 on what is left).

## 2. Method (`--friction-fit`)

Per joint (J1-J5) and per segment (0 approach, 1 trajectory, 2 return) of the `path` rows: least squares of e and of
τ − τ_ff on [1, tanh(v_ref/0.02), v_ref, a_ref], v_ref and a_ref by `np.gradient` of the logged ref. Reported: the four
coefficients and R² of each fit; the sign term in mrad and × kp; the **implied Coulomb** = the run's Coulomb
feed-forward (read from the run summary, so a run with `--friction` is scored against what it used) + the torque fit's
sign coefficient, also split by direction; the VIF of the sign column (flag > 15: confounded with the constant);
the correlation and the **coherence** of the joint's error with J3's (Welch, Hann, 5.1 s segments; largest value in
2.5-3.5 Hz, the 95 % zero-coherence level for that many segments, and the 2.5-40 Hz band rms split into shared/own);
and the **what-if** (`--what-if-friction j4=X`: e + (F_run − X)/kp × tanh; `--what-if-kp j4=K`: × kp_run/K). Several
runs: the across-run mean / sd of the implied Coulomb. `--seg1-window T0:T1` restricts everything to a part of the
trajectory (file seconds × the run's slow), e.g. one pose of `j4_tune.json`. `--compare` gained a hold-flip count
(measured-velocity sign changes with |v| > 0.05 rad/s while |v_ref| < 0.005, CONTROLLER_TUNING §8).

Limits (details in the evidence README): `ref` is logged to 0.1 mrad, so a_ref is mostly quantisation noise (the
inertia coefficient means nothing, but is bounded < 0.01 Nm); coherence from 3-8 segments is biased upward; the what-if
is quasi-static. **Validation on the fake plant** (fakebus J4: Coulomb 0.3, viscous 0.5, inertia 0.07): from the
j4_tune rehearsal the fit recovered the plant's Coulomb (implied 0.31; up/down 0.33/0.29), and again 0.30 from a
rehearsal with `--friction j4=0.3`, whose sign term was +0.0 mrad against +0.3 predicted. The predicted rms was
conservative there (3.5 → simulated 1.7 mrad at the heart pose; 5.8 → 4.0 at the crack pose), because the fake plant's
fit has R² 0.41; the real arm's is 0.9.

## 3. The runner option `--friction` (demo_move.py 2026-10-29.2)

- `--friction jN=X[,jM=Y]`: for this run the Coulomb feed-forward of those joints is X Nm instead of
  `first_move_j1.TUNED`'s (J4 0.5). 0 ≤ X ≤ `first_move_j1.FRICTION_MAX_NM` (3.0), joints j1-j6 only; anything else is a
  usage error before the bus is opened.
- It replaces the value in the one place both feed-forward functions read it (`FRICTION`), so it applies with and
  without `--gravity-model` (including that option's Coulomb trim at the caps), and the arm_guard pre-flight checks the
  run with it. Caps, gains, aborts and the guard are unchanged. It combines with `--gains` / `--ff-bias` /
  `--gravity-model`.
- The run summary records `friction` (as used) and `friction_override`; the log gets a line, e.g.
  `Coulomb friction feed-forward for this run: j4 0.18 Nm (tuned 0.5)`. `FRICTION` is restored after the run, like
  `GAINS` and `GRAV_SCALE`.
- **Byte-identical default:** `run-trajectory.sh --rehearse trajectories/fancy/heart.json` wrote the same CSV before
  and after the change (md5 `29beb50f31108975c2421428fb0e3d8c`, the same as before the gravity-model change), and
  `test_without_the_flag_the_command_stream_is_byte_identical_to_both_pre_change_runners` compares every enable, MIT
  command and disable of a guarded smoke run against the copies in `~/rebot_setup/backup_pre_j4_friction_2026-10-29/`
  and `backup_pre_gravity_model_2026-10-29/`.
- **`run-trajectory.sh --rehearse` ignores `DEMO_EXTRA`** (only `--check` and real runs pass it; verified again:
  `DEMO_EXTRA="--friction j4=0.18" … --rehearse heart.json` wrote the default CSV, `friction_override: {}`). Rehearsals
  with the A/B overrides are therefore tests calling the runner in-process with the `--rehearse` arguments:
  `test_j4_tune_rehearsals_with_the_ab_overrides_pass_the_guard` (C: `--friction j4=0.18 --gains j4=40/3`, D:
  `--friction j4=0.18 --gains j4=50/3`, and `--gains j4=50/3` alone), plus a one-off in-process rehearsal with
  `--friction j4=0.3` (the what-if check of §2): all completed, guard pre-flight clean, no guard fault. **Fixed 2026-10-29 (after this was written): the wrapper's rehearse branch now passes `${DEMO_EXTRA:-}`; backup in `~/rebot_setup/backup_pre_rehearse_extra_2026-10-29/`, verified with `DEMO_EXTRA="--friction j4=0.18 --gains j4=40/3" … --rehearse j4_tune.json 2` (summary shows both overrides).**

## 5. Predictions, written before any arm run

A … E are the runs of §6. Windows (`--seg1-window T0:T1`) are seconds of trajectory-file time **from the start of
the trajectory segment** (the tool multiplies by the run's slow from its summary). The tool finds that segment by its
kind from the run summary's `path_kinds` (demo_move.py 2026-10-29.3+), not by its number: j4_tune.json starts and ends
at the fold, so with `--j1-here-is-zero` (after a power cycle) the zero-length approach and return are dropped and the
trajectory is segment 0; with the saved J1 reference it usually has a short approach and is segment 1. Either way the
windows below and `--compare` refer to the same part of the file. "rms" is the tool's (standard deviation about the
mean). Tolerances are stated so each line can fail. **Keep every run's `.json` next to its `.csv` and do not rename
either:** without it the tool assumes slow 1, the tuned kp / Coulomb values and segment 1 (a loud WARNING, and the
output is marked), which would put every window in the wrong place for an x2 run.
